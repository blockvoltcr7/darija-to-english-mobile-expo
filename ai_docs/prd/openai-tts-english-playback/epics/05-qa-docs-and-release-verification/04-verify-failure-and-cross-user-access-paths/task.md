# Task 04: Verify Failure And Cross-User Access Paths

## Type

Code

## Context

The feature is not release-ready until negative paths are verified. TTS must fail gracefully, and generated audio must remain inaccessible to other users.

## Implementation

- Force or simulate TTS provider failure and confirm text translation remains succeeded.
- Confirm failed TTS is represented as safe metadata in API detail and diagnostics.
- Create or use a second Clerk test user to request another user's playback route.
- Confirm cross-user playback receives 404 or the chosen safe non-disclosing error.
- Confirm unauthenticated playback fails.
- Review API and Trigger logs for accidental leakage of secrets, tokens, full text, private audio contents, or generated bytes.

## Acceptance Criteria

- [ ] Forced TTS failure does not remove or hide the English translation.
- [ ] Failed TTS artifact records safe error metadata.
- [ ] Cross-user playback access is denied.
- [ ] Unauthenticated playback access is denied.
- [ ] Logs and QA artifacts contain no secrets, private audio contents, full transcripts, or generated audio bytes.

## Dependencies

- Depends On: run-fresh-user-tts-qa

## Technical Notes

- Prefer 404 for cross-user artifact access to avoid confirming resource existence.
- Keep test identities redacted in durable docs unless a non-sensitive test email is explicitly acceptable.

## Artifact Slots

- `artifacts/`: negative-path QA summary and sanitized API response examples.
- `references/`: playback route checks and PRD risk assessment.
- `resources/`: curl templates with placeholder tokens only.
- `notes/`: failure-mode observations and release blockers.
